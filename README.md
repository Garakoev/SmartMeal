# SmartMealService — тестовое задание C# Middle

Два задания из PDF: DLL с HTTP/gRPC-клиентами и консольное приложение с PostgreSQL; WPF-редактор переменных среды. Все приложения ориентированы на **.NET 8**, WPF запускается в Windows.

## Состав решения

| Проект | Назначение |
|---|---|
| `Sms.Client` | `Sms.Client.dll`: модели блюда и заказа, общий `ISmsClient`, HTTP и gRPC |
| `Sms.ConsoleApp` | Получение меню, создание БД/таблицы, сохранение меню и отправка заказа |
| `Sms.WpfApp` | Редактор постоянных переменных среды текущего пользователя Windows |
| `Sms.Common` | Чтение настроек, ежедневные логи, запись консольного сеанса |
| `Sms.DemoServer` | Локальный HTTP/gRPC-сервер с примерами из задания |
| `Sms.Tests` | Проверки контрактов, ошибок, консольного сценария, WPF и PostgreSQL |

Адресов сервера работодателя в задании нет. Для воспроизводимой проверки добавлен демонстрационный сервер. Для работы с настоящим сервером достаточно изменить настройки клиента.

## Требования

- Windows 10/11 для WPF и полного набора тестов.
- .NET SDK 8.0 или более новый, поддерживающий сборку `net8.0`. `global.json` допускает использование установленного более нового SDK. Для запуска нужна среда .NET 8 Desktop Runtime (при установке SDK 8 на Windows она входит в комплект).
- PostgreSQL: локальный сервер либо Docker Desktop с Linux containers. Docker для самой программы не требуется.
- Доступ к nuget.org при первом восстановлении зависимостей.

Открыть `SmartMealService.sln` в Visual Studio 2022 17.8+ / Rider или работать из терминала в корне репозитория:

```powershell
dotnet restore SmartMealService.sln
dotnet build SmartMealService.sln -c Release --no-restore
```

## Настройка локального PostgreSQL

Используйте хост, порт и пользователя из DBeaver. Следующий скрипт запрашивает пароль без отображения на экране и сохраняет локальные настройки, исключённые из Git:

```powershell
.\scripts\Configure-LocalPostgres.ps1 -Server localhost -Port 5432 -Username postgres
```

Альтернатива: скопировать `src/Sms.ConsoleApp/appsettings.local.example.json` в `src/Sms.ConsoleApp/appsettings.local.json` и заполнить пароль. Файл `appsettings.local.json` перекрывает основные настройки и копируется рядом с приложением при сборке. Не загружайте его в репозиторий и не передавайте в архиве с исходниками.

Консольное приложение само создаёт **отдельную БД `sms_test`** и таблицу `public.menu_items`, если они отсутствуют. Для создания БД пользователю требуется `CREATEDB` и возможность подключиться к служебной БД `postgres`. Если `sms_test` уже создана, `CREATEDB` не требуется; нужны права подключения, создания таблицы и записи. Ранее существовавшие данные других БД приложение не меняет.

### Альтернатива: PostgreSQL в Docker

Без локальных настроек приложение использует демонстрационные реквизиты из `appsettings.json`:

```powershell
docker compose up -d --wait
```

PostgreSQL доступен на `localhost:55432`, пользователь `sms_demo`, пароль `sms_demo_password`. Это только демонстрационные реквизиты. В контейнере первоначально существует БД `postgres`; `sms_test` создаёт консольное приложение. Порт отличается от стандартного, чтобы не конфликтовать с локальным PostgreSQL.

```powershell
docker compose stop
```

Остановка сохраняет данные в именованном томе.

## Запуск задания 1

В первом терминале запустить демонстрационный сервер:

```powershell
dotnet run --project src/Sms.DemoServer --no-launch-profile
```

Он слушает HTTP на `http://localhost:5080/api` и gRPC (HTTP/2) на `http://localhost:5081`. Проверка доступности: `http://localhost:5080/health`. Basic-логин и пароль для HTTP: `demo` / `demo`. gRPC не требует авторизации.

Во втором терминале:

```powershell
dotnet run --project src/Sms.ConsoleApp
```

Пример ввода:

```text
A1004292:1;A1004293:0.408
```

Приложение показывает блюда в формате `Название – Артикул – Цена`, сохраняет меню в PostgreSQL, запрашивает заказ и выводит `УСПЕХ` либо текст ошибки. При ошибочном вводе предлагает повторить ввод. `Ctrl+C` отменяет операцию; конец входного потока завершает работу без отправки заказа.

Переключение на gRPC без изменения файлов:

```powershell
$env:SMS_Api__Transport = 'Grpc'
dotnet run --project src/Sms.ConsoleApp
Remove-Item Env:SMS_Api__Transport
```

Либо изменить `Api:Transport` на `Grpc` в `appsettings.local.json`. Для настоящего сервера задайте `HttpEndpoint` / `GrpcEndpoint`, а для HTTP также `Username` / `Password`. HTTP-клиент использует один endpoint для обеих команд. Basic следует применять через HTTPS вне локальной демонстрации.

Приоритет настроек: `appsettings.json` → `appsettings.local.json` → переменные с префиксом `SMS_`. Вложенность обозначается `__`, например `SMS_ConnectionStrings__Postgres`. Файлы читаются относительно каталога исполняемого приложения, а не текущего рабочего каталога.

### Использование DLL

После сборки библиотека находится в `src/Sms.Client/bin/Release/net8.0/Sms.Client.dll`. Её зависимости также нужны при использовании вне решения. Внутри решения подключена через `ProjectReference`, который при сборке создаёт и копирует DLL.

```csharp
using Sms.Client;

using var http = new HttpClient { Timeout = TimeSpan.FromSeconds(30) };
ISmsClient client = new HttpSmsClient(http, new Uri("http://localhost:5080/api"), "demo", "demo");
ApiResult<Dish[]> menu = await client.GetMenuAsync();
ApiResult<bool> sent = await client.SendOrderAsync(
    new Order(Guid.NewGuid(), [new OrderItem("5979224", 1m)]));
```

У `GrpcSmsClient` тот же интерфейс; в конструктор передаётся `GrpcChannel`. Владельцем `HttpClient` и `GrpcChannel` является вызывающий код. Отмена передаётся через `CancellationToken`; отмена пользователем не маскируется под ответ сервера.

## Запуск задания 2

```powershell
dotnet run --project src/Sms.WpfApp
```

Интерфейс повторяет элементы макета: белое скруглённое окно, жёлто-зелёное свечение, кнопки сворачивания и закрытия, таблица «Поле / Значение / Комментарий». Точные размеры не фиксированы; окно можно растягивать за нижний правый угол.

- Двойной щелчок или F2 в столбце «Значение» начинает редактирование.
- `Tab`, `Ctrl+Enter` или переход к другой ячейке сохраняет значение.
- `Enter` внутри редактора добавляет новую строку; `Esc` отменяет редактирование.
- Закрытие окна завершает редактирование. Если сохранение невозможно, окно остаётся открытым, а причина отображается внизу.
- Имена и комментарии не редактируются; они заданы конфигурацией.

В `src/Sms.WpfApp/appsettings.json`:

- `EnvironmentVariables` — требуемый массив имён;
- `DefaultValues` — значения для отсутствующих переменных (если нет записи, используется пустая строка);
- `Comments` — пояснения для третьего столбца;
- `LogDirectory` — каталог логов.

По умолчанию используются только `SMS_DEMO_SERVER`, `SMS_DEMO_TERMINAL`, `SMS_DEMO_DESCRIPTION`. Значения сохраняются в `HKEY_CURRENT_USER\Environment`, доступны приложениям текущего пользователя и переживают перезапуск ОС. Права администратора не нужны. Уже существующие значения при запуске не заменяются значениями по умолчанию.

## Логи

Логи создаются в `logs` рядом с соответствующим исполняемым файлом (или в каталоге `LogDirectory`):

- `test-sms-console-app-yyyyMMdd.log` — stdout, stderr и введённые пользователем строки;
- `test-sms-wpf-app-yyyyMMdd.log` — JSON-строки с временем, действием, именем переменной, прежним и новым значениями.

Файл выбирается на каждую запись: после полуночи используется новая дата. Логи дописываются, а не перезаписываются. WPF регистрирует и первоначальное создание отсутствующих переменных. Значения редактируемых переменных попадают в лог по назначению приложения; не включайте в демонстрационный набор пароли или токены.

## Проверка

```powershell
.\scripts\Verify.ps1
```

Без БД выполняются тесты HTTP-контракта, Basic-аутентификации, gRPC через настоящий локальный HTTP/2-сервер, ошибок и отмены, разбора заказов, консольного сценария, ежедневных логов, сохранения переменных через тестовое хранилище и построения WPF-интерфейса. Тест с PostgreSQL явно помечается пропущенным.

Для полного прогона с локальным PostgreSQL после настройки подключения:

```powershell
.\scripts\Verify.ps1 -WithPostgres
```

Интеграционный тест создаёт уникальную временную БД `sms_it_<guid>`, проверяет создание таблицы, повторную инициализацию, вставку и обновление меню и затем удаляет **только свою БД**. Нужен пользователь с `CREATEDB`. Можно также задать строку подключения к служебной БД через `SMS_TEST_POSTGRES` и вызвать `dotnet test` напрямую.

Для проверки настоящего хранилища переменных Windows добавьте `-WithEnvironment`. Этот тест создаёт уникальную переменную `SMS_IT_<guid>` текущего пользователя, читает её из другого процесса, проверяет пустое значение и удаляет свою переменную в конце. Без флага тест явно пропускается; существующие переменные пользователя тест не меняет.

Проверка консольного приложения при запущенном демонстрационном сервере:

```powershell
.\scripts\Smoke-Test.ps1 -Transport Http
.\scripts\Smoke-Test.ps1 -Transport Grpc
```

В `artifacts/TestResults` сохраняется отчёт TRX; тест интерфейса создаёт `artifacts/wpf-preview.png`. Настроен GitHub Actions для сборки и тестов в Windows; БД в этом задании CI не запускается, соответствующий тест будет пропущен.

## Принятые допущения и детали

1. Реализованы **оба** транспорта. `.proto` соответствует приложению №3; созданные из него классы лежат в `Sms.Test`, прикладные модели — в `Sms.Client`.
2. HTTP использует POST. При HTTP 200 проверяется `Success`; `ErrorMessage` возвращается вызывающему коду. Дополнительно обрабатываются сетевые ошибки, тайм-ауты, неожиданные HTTP-статусы и некорректный JSON. Автоматических повторов отправки заказа нет: ответ мог потеряться после принятия заказа сервером.
3. «Код» при вводе — **Article**, в запрос отправляется **Id**. Артикулы сравниваются без учёта регистра; повторённые позиции суммируются. Пробелы по краям и завершающая точка с запятой разрешены. Дробная часть может отделяться точкой или запятой. Любое количество должно быть больше нуля; дополнительного ограничения на целое количество для невесового блюда в ТЗ нет.
4. Прикладные цена и количество используют `decimal`. В HTTP `Quantity` сериализуется **строкой** с точкой, как в примере. В gRPC используются `double`, потому что так задан контракт; возможна соответствующая потеря точности при преобразовании.
5. Меню сохраняется транзакцией через параметризованный SQL. Повторный запуск обновляет строки по `Id`, не создаёт дубликатов и не удаляет блюда, отсутствующие в новом ответе. Для создания новой БД имя экранируется как SQL-идентификатор.
6. Постоянные переменные относятся к **текущему пользователю**, а не ко всем пользователям компьютера. После сохранения отправляется `WM_SETTINGCHANGE`. Новые приложения, запускаемые обновившим окружение Explorer, наследуют значения; уже запущенные процессы не обязаны обновлять собственное окружение. Их нужно перезапустить или явно перечитать значения.
7. «Практически без ограничений по длине» трактуется как отсутствие короткого лимита поля ввода. Поддерживаются многострочные значения и десятки тысяч символов в пределах Windows: максимум 32 766 символов значения, без NUL. Выход за предел обнаруживается до записи. Хранилище напрямую использует `REG_SZ`, чтобы **пустое значение не удаляло переменную**, как это делает `Environment.SetEnvironmentVariable` в .NET 8.
8. Значения по умолчанию и комментарии не определены ТЗ, поэтому вынесены в настройки. Сохранение выполняется при завершении редактирования. Если значение изменилось извне после загрузки, редактор показывает конфликт и перечитывает значение вместо молчаливой перезаписи.

Ограничения Windows: [переменные среды](https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables), [поведение Environment.SetEnvironmentVariable](https://learn.microsoft.com/en-us/dotnet/api/system.environment.setenvironmentvariable?view=net-8.0).
